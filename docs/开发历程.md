# 巴别塔：从第一次录音到公开预览版

本文依据仓库真实 Git 提交和开发中的问题整理。日期以提交记录为准；早期的使用探索、Python 入门提问没有独立提交，不补造日期。开发者是一名在校大学生，以学习和个人使用需求为起点，开发中使用 AI 编程辅助工具，一边实现功能、一边理解原理。

## 起点：希望看懂不同语言的视频

最初的需求是为中文及其他语言的视频提供实时中文字幕。试用 LiveTranslate 时，曾出现播放网页视频却没有字幕、音量条不动、识别与翻译计数一直为零的问题。排查时逐渐分清了系统输出设备、麦克风和 WASAPI 回环录音：模型启动成功不代表声音已进入识别流程，首先应确认采集链路。

试用也带来了后来的产品想法：简化专业设置，改善界面，提供 EXE；记录 token 与费用；支持免费或本地模型；为已有视频导出时间正确的字幕，并可封装进视频。字幕烧录暂缓。

参考 LiveTranslate 的功能思路后，本项目从自己的 Python 工程开始实现，没有直接复制或合并其应用源代码。底层模型与第三方库仍依赖各自开源项目，不能把这些成果视为本项目原创。来源和许可见 [NOTICE](../NOTICE.md)。

## 2026-10-07：建立自己的应用骨架

相关提交：`799d190`、`75230d3`、`6d73261`。

创建 Python 桌面应用工程并与已有仓库说明合并，建立独立的目录和入口。这一阶段也在学习：PowerShell/CMD 的作用是调用程序，Python 负责执行代码；`pip` 是依赖管理工具，不是命令行自动扫描代码安装依赖；`python -m` 表示按模块入口运行。

窗口由 PyQt6 创建，Python 文件提供窗口、按钮、事件处理逻辑，事件循环持续响应操作。源码不是“编译成窗口”，而是执行后调用界面库构造窗口；后来的 EXE 则会把解释器和依赖一起收集。

## 2026-10-08：先把系统声音可靠地录下来

相关提交：`b3e949e`、`e992c3c`。

通过 PyAudioWPatch 的 Windows WASAPI loopback 采集输出设备正在播放的声音，保存 WAV。它录制的是播放器输出，不是默认拿麦克风对着扬声器录音。采集放到工作线程，主界面显示音量变化和设备信息。

不同设备可能输出 48 kHz、多声道音频，而识别流程需要统一格式，因此增加混音与持续重采样，转换为 16 kHz、单声道、16 位 PCM。音频缓存、线程通信、文件写入和异常清理开始从窗口代码中分离。

## 2026-10-10 至 10-11：接入 VAD、Whisper，并处理中文问题

相关提交：`9c8cdb3`、`65a1371`、`4c1d80f`、`dac30f8`。

加入 WebRTC VAD 判断哪些片段含有人声，再通过 faster-whisper 调用 Whisper 模型识别。理解了这几层的关系：库负责加载模型、处理输入和执行推理；模型权重来自开源 Whisper，本项目没有训练自己的语音模型。

实际测试中，朗诵、配乐、生僻词、短片段和词语被截断都会影响结果。多声道设备还可能只有少数声道有人声，简单平均会降低音量，因此改进了声道混合。加入非语音过滤，减少把音乐或空白当语音解码的情况。用 OpenCC 将中文识别结果统一转换为简体字。

使用《百年沧桑》《白杨礼赞》《明朝那些事》等朗读材料做过对比观察，也发现日常叙述与有配乐的朗诵表现不同。这些是测试与比较，不是对模型进行训练，也不能据此声称已证明模型的总体准确率。

## 2026-10-20：通过对比与字幕文件走向可用工具

模型对比提交：`ec7e68e`。

加入离线评测流程，对同批 WAV 比较 small、medium，记录逐段结果和耗时，提供可浏览的报告。只有与录音逐字对应、经过人工核对的参考文字才适合用于准确率评分；网上原文或自动稿标为草稿，避免把版本差异当成模型错误。最终决定先以 small 的速度和识别能力继续完善产品。

导出与视频处理提交：`5c74044`、`0bba3ae`。

实现 TXT 和 SRT 导出，使用音频位置和模型时间戳生成字幕，而不是把“识别完成的时刻”写成字幕时间。进一步通过 PyAV 直接读取本地视频音轨，保留媒体时间轴、音轨延迟和间隔。已有文件另存编号版，取消或中断时保留可用的部分结果。

预览与校对提交：`db58ce9`。

加入本地视频/录音预览、字幕列表、逐条修改文字及起止时间、另存校对 SRT。自动时间戳可以帮助初稿生成，但不能替代人工校对，尤其是暂停、剪辑、配乐与重叠人声场景。

## 2026-10-21：翻译、字幕封装、用量和便携包

翻译与封装提交：`dd0dd1b`。

使用兼容 `/chat/completions` 的外部接口翻译字幕，提供千问、Ollama 和自定义地址。只发送字幕文字，要求模型返回带编号的 JSON，使译文能映射回原字幕并保留时间。使用 FFmpeg 将字幕封装为 MKV 软字幕轨，保持视频与音频直接复制，暂不实现烧录。

用量与费用提交：`ec0de78`。

读取接口返回的输入、输出 token，允许用户填写单价，分别估算人民币或美元费用并导出报告。缺失的用量标为未知，不能当成零；接口超时也不能据此断定服务商没有计费。API Key 不写入配置或报告。

打包提交：`a436334`。

使用 PyInstaller 生成 Windows 目录式便携 EXE，收集 Python、Qt、多媒体库和 small 模型。加入实际 EXE 自检，验证包内依赖、模型加载、模拟翻译和封装，减少“源码能跑但 EXE 不能跑”的问题。

## 2026-10-23：简化界面，做出直播字幕框

界面与缓存提交：`3630c7a`、`c5ab123`。

将主要操作分成视频处理与电脑声音识别，收起专业选项。默认使用独立的临时录音会话，用户不再每次选择 WAV 保存位置；关闭或下次任务清理本会话缓存。需要保留录音时才选择保存路径，并保护目录中的其他文件。

悬浮字幕提交：`efe89dd`。

用户明确需要屏幕上可拖动的字幕框，而不只是主窗口显示原文。因此增加置顶、半透明、可拖动和隐藏恢复的字幕窗口，把逐段识别接入独立翻译队列。停录后继续处理最后一段；取消或关闭时结束相关任务。

## 2026-10-24：命名为巴别塔，并正视实时延迟

命名提交：`4c9c56b`。

项目正式取名“巴别塔”，寓意消除语言隔阂。设计层叠塔身与金色通道的图标，生成七种尺寸的 ICO，统一窗口、EXE 名称和 Windows 产品属性。内部设置与缓存目录保持兼容。

性能优化提交：`ea3cd99`。

实际使用发现，实时字幕比预期慢，而文件处理相对可用。代码检查找出了固定使用 CPU、完整识别参数、较长分段和待识别队列积压等原因。原有测试证明了基本功能，却没有证明直播场景下的延迟足够好，这成为一次直接的工程教训。

为系统声音模式增加 NVIDIA GPU / float16，补齐并随包收集 cuBLAS、cuDNN、NVRTC；通过真实推理验证 GPU，而不只检查“能检测到显卡”。GPU 不可用时说明原因并回退 CPU。实时模式降低搜索量，关闭逐词对齐和重复 VAD；识别与翻译各只保留一个等待项，跟不上时优先处理新内容，并显示跳过数量。

同一段 8 秒英文样本预热后的识别耗时，从原 CPU 配置约 1.346 秒降至 GPU 实时配置约 0.137 秒。它只代表该样本的识别阶段，不含分段和翻译，更不表示所有视频都能快十倍。详见 [实时性能优化](实时性能优化.md)。
